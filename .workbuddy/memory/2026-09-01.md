## FishSpeech 1.5 统一语音处理服务（USS）—— 交付完成

在 RTX 3060 12GB 上基于 FishSpeech 1.5 构建了统一语音服务，集成口型同步 / 字幕识别 / 语音克隆三项能力。

### 交付物
- `service/` — FastAPI 服务（server.py / config.py / gpu.py / concurrency.py + engines/）
- `tests/` — 三项功能端到端测试 + 并发压测 + 容量测试
- `README.md` — 架构、依赖安装、3060 显存配置、API 文档与调用示例
- `REPORT.md` — 三项功能测试报告（精度、失败异常、限制、改进建议）
- `PERFORMANCE.md` — 性能分析报告（单项基准、并发、容量规划）

### 实测结果

|---|---|---|
| ASR | 字准确率 | 97.59%，段起点偏差 −0.7ms，RTF 0.132 |

### 性能瓶颈（重要）
- **TTS 是绝对瓶颈**：6.2 req/min，仅为 ASR（44.4）的 1/7，根因 dual-AR 自回归 RTF≈1.95
- **单卡吞吐上限 ~18 req/min（混合负载），不随并发提升** — 并发 8 效率仅 13%
- 容量：纯 TTS 场景 ~6 人，混合场景 ~18 人，纯 ASR/口型 ~40 人

### 已实施优化：TTS 结果缓存（service/tts_cache.py）
- key = sha256(文本 | 参考音频**内容** | 参考文本 | 解码参数)；LRU 淘汰，默认上限 500 条
- 参考音频按内容而非路径摘要（改名/移动不影响命中，内容变了一定不误命中）
- 写入用「临时文件 + 原子替换」，避免并发下读到半截 wav
- **实测收益：固定话术场景命中率 75% 时，吞吐 5.8 → 27.8 req/min（4.84x），
  平均延迟 10.44s → 2.15s**
- 端点：GET /v1/cache/stats（命中率）、POST /v1/cache/clear；/v1/tts 响应加 `cached` 字段
- 环境变量 USS_TTS_CACHE(1) / USS_TTS_CACHE_MAX(500)
- **只对重复文本有效**（固定话术/批量配音）；实时对话类文本唯一场景收益为 0

### 关键 Bug 与修复（可复用经验）
1. **事件循环阻塞**：`async def` 端点内直接调用同步推理 → 独占事件循环，
   并发 8 时 `/health` 延迟达 31 秒（饿死 6113 倍）。
   修复：`service/concurrency.py` 用 `run_in_threadpool` + 按模型分组信号量
   （同类串行/异类并行/全局额度 2）。修复后 104ms（298 倍改善），成功率 84%→100%。
   **注意：吞吐上限不变，买到的是"响应性"不是"吞吐"。**
2. **speechbrain LazyModule 重入死循环**：`ensure_module()` 调 `inspect.getframeinfo`
   → `getmodule` 遍历 sys.modules 取 `__file__` → 又碰到代理 → 无限递归。
   上游守卫 `endswith("/inspect.py")` 在 Windows 反斜杠路径 + embeddable zip 标准库下失效。
   修复：`_patch_speechbrain_lazy()` 加重入锁，在服务启动钩子应用。
3. **faster-whisper `speech_pad_ms` 默认 400** 导致段起点系统性偏早 −370ms
   （前置填充静音让 Whisper 把首段预测到 0）。改 30ms 后降到 −0.7ms。
4. **PEP 420 空壳包陷阱**：site-packages 中包目录被清空但目录仍在，
   `import` 会"成功"（`__file__=None`）实则空壳。曾影响 10 个包。
   修复：`--no-deps --ignore-installed` 批量重装 + 校验 `__file__` 非空。
5. **全局 `except Exception` 吞掉 `HTTPException`** → 404 变 500。加 `except HTTPException: raise`。
6. FishSpeech 克隆必须 `prompt_text` 与 `prompt_tokens` 成对，否则静默退化为随机音色。
7. **显存观测盲点**：`torch.cuda.memory_allocated()` 不含 CTranslate2 显存池，
   ASR 显存显示为 0。监控需用 `nvidia-smi` 或 pynvml。

### 已实施优化 2：异步任务化（service/jobs.py）
- 排队在单卡上是物理必然（TTS 6.2 req/min），异步化把它显式化、可观测
- 端点：POST /v1/jobs（提交，毫秒级返回）、GET /v1/jobs/{id}（状态+queue_pos）、
  GET /v1/jobs（列表+统计）、DELETE /v1/jobs/{id}（取消）
- 同步端点保持不变，抽出 _do_asr/_do_tts/_do_lipsync 与异步任务共用，行为一致
- 异步任务只接受服务端路径，不支持文件上传
- 冷路径实测 4 个 TTS：端到端 9.57/19.39/31.75/40.42s，queue_pos 正确反映排队
- 用 asyncio + 内存队列（不引入 celery/redis）；代价是重启丢任务列表（结果文件仍在）
- 踩坑：Job dataclass 用 asdict() 会 deepcopy `_task: asyncio.Task` 而报
  "cannot pickle '_asyncio.Task'"，to_dict 必须手动构造字段

### 重构注意

### TTS 瓶颈剖析结论（tests/profile_tts.py 实测）
- 实测显存带宽 267 GB/s；LLM 637.9M 参数 / 1217 MB (bf16)
- 生成 9.8 tokens/s，每 token 102ms；有效带宽仅 ~12 GB/s = 实测带宽 4.5%
- **每 token 约 11000 次 kernel launch**
- 非计算开销（搬运 + 视图整形）占 ~45%：as_strided 277k 次、view 128k 次、
  copy_ 76k 次、_to_copy 61k 次
- 结论：瓶颈是「大量碎小算子」不是算力 -> 降精度/减权重收益有限
- **torch.compile 不可用**：Windows 官方 wheel 不含 triton
- 官方日志 "Bandwidth achieved" = model_size × tokens_sec，
  不是真实显存带宽，切勿与标称带宽比较
- 坑: PyTorch 2.x 把 profiler 的 self_cuda_time_total 改名为
  self_device_time_total，用旧名会静默取到 0
- CUDA Graph 是理论正解（消除 launch 开销），但需改 dual-AR 解码循环，风险高
